# Загрузка и хранение файла встречи

Status: ready-for-agent

Источник: [PRD](../../docs/specs/meeting-file-upload.md).

## Problem Statement

Владелец может создать встречу с названием, датой и участниками, но не может прикрепить запись. Запись приходится хранить отдельно, связь со встречей теряется, а последующая обработка не имеет надёжного источника файла.

## Solution

Владелец открывает встречу, выбирает файл записи и загружает его. После успешного сохранения внутри встречи отображаются название файла, размер, тип и время загрузки. Файл остаётся доступным после обновления страницы и перезапуска приложения; владелец может скачать оригинал. Сохранённая запись становится источником для будущей обработки, которая не входит в этот этап.

## User Stories

1. As a владелец встречи, I want to открыть детали встречи из списка, so that я могу работать с её записью.
2. As a владелец встречи, I want to видеть название, дату и участников в деталях, so that я понимаю, к какой встрече прикрепляю файл.
3. As a владелец встречи, I want to видеть отсутствие записи, so that я понимаю, что файл ещё нужно загрузить.
4. As a владелец встречи, I want to выбрать файл на устройстве, so that я могу прикрепить существующую запись.
5. As a владелец встречи, I want to знать допустимые форматы и размер заранее, so that я выбираю подходящий файл.
6. As a владелец встречи, I want to видеть имя и размер выбранного файла до отправки, so that я могу проверить выбор.
7. As a владелец встречи, I want to изменить выбор до отправки, so that я могу исправить ошибку.
8. As a владелец встречи, I want to явно начать загрузку, so that выбор файла не запускает неожиданное действие.
9. As a владелец встречи, I want to видеть состояние загрузки, so that я понимаю, что запрос ещё выполняется.
10. As a владелец встречи, I want to защиту от повторного нажатия, so that я не создаю дубликаты.
11. As a владелец встречи, I want to получить подтверждение сохранения, so that я знаю, что запись доступна серверу.
12. As a владелец встречи, I want to видеть метаданные сохранённого файла, so that я могу идентифицировать запись.
13. As a владелец встречи, I want to видеть запись после перезагрузки страницы, so that я не завишу от состояния браузера.
14. As a владелец встречи, I want to скачать оригинал, so that я могу использовать запись вне приложения.
15. As a владелец встречи, I want to получить понятную ошибку неподдерживаемого формата, so that я могу выбрать другой файл.
16. As a владелец встречи, I want to получить понятную ошибку слишком большого или пустого файла, so that я могу исправить загрузку.
17. As a владелец встречи, I want to повторить загрузку после сетевой ошибки, so that временный сбой не блокирует работу.
18. As a владелец встречи, I want to видеть фактически сохранённый файл после неопределённого результата запроса, so that повторная попытка не создаёт вторую запись.
19. As a владелец встречи, I want to сохранить приватность записи, so that другие аккаунты не могут читать или менять её.
20. As a пользователь с истёкшей сессией, I want to получить предложение войти снова, so that я могу продолжить работу безопасно.
21. As a пользователь мобильного устройства, I want to загружать и просматривать запись в адаптивном интерфейсе, so that мне не нужен компьютер.
22. As a пользователь клавиатуры или экранного диктора, I want to доступные элементы выбора и сообщения состояния, so that я могу самостоятельно загрузить запись.
23. As a оператор приложения, I want to сохранить файлы при перезапуске контейнеров, so that загруженные записи не теряются.
24. As a разработчик последующей обработки, I want to получить устойчивый идентификатор и серверное расположение сохранённой записи, so that обработка использует полный оригинал.

## Implementation Decisions

- Существующий стек: Vue 3, TypeScript, FastAPI, Pydantic 2, async SQLAlchemy, PostgreSQL и Alembic. Сохраняются JWT-авторизация, общий HTTP-клиент и генерация типов из OpenAPI.
- Добавить экран деталей встречи и переход из существующего списка. Загружать файл только в уже созданную встречу; создание встречи остаётся самостоятельной операцией.
- Одна аудио- или видеозапись на встречу или любой другой поддерживаемый формат. Также поддерживается удаление или замена файлов.
- Предлагаемые ограничения, пока не подтверждённые требования: MP3, WAV, M4A, TXT, MD, MP4 и WebM; максимум 500 MiB; пустой файл запрещён. Ограничение размера задаётся конфигурацией сервера и согласуется с прокси. Интерфейс показывает фактическое ограничение, полученное от API.
- Сервер проверяет размер при чтении потока, допустимость расширения и типа содержимого. Проверка не опирается только на MIME, переданный браузером. Клиентская проверка помогает пользователю, но не является границей безопасности.
- Бинарный оригинал хранится в выделенном постоянном volume приложения; PostgreSQL хранит только метаданные. Это минимальная схема для текущего Compose-развёртывания с одним файловым хранилищем. Объектное хранилище и несколько независимых API-узлов не входят в этап.
- Новая сущность записи связана внешним ключом со встречей; уникальность связи обеспечивает один файл на встречу при конкурентных запросах. Метаданные: ID файла, ID встречи, исходное имя, фактический размер, проверенный тип, время загрузки и внутренний ключ хранения. Внутренний путь не возвращается клиенту.
- Миграция добавляет сущность без изменения существующих встреч. Отсутствие файла — штатное состояние.
- Предлагаемый контракт: POST /meetings/{id}/file принимает multipart/form-data и возвращает метаданные с 201; GET /meetings/{id}/file возвращает метаданные либо 404; GET /meetings/{id}/file/content возвращает оригинал как вложение. GET /meetings/{id} сохраняет прежний контракт. Дополнительно GET /meetings/file-upload-options возвращает допустимые форматы и лимит, не раскрывая настройки хранения; статический маршрут регистрируется до маршрута с ID встречи.
- Все операции проверяют владельца на backend. Чужая или отсутствующая встреча возвращает 404; отсутствующая авторизация — 401; конфликт — 409; превышение размера — 413; неподдерживаемый тип — 415; пустой или некорректный файл — 422.
- Файл записывается потоково во временное расположение и становится доступным только после полного сохранения и фиксации метаданных. Имена объектов генерирует сервер; пользовательское имя не используется как путь. Ошибки записи, фиксации БД и конкурентной загрузки требуют очистки незавершённых объектов. Авария между файловой операцией и транзакцией может оставить сироту: предусмотреть явную процедуру сверки и очистки, не удаляющую связанные файлы.
- Проверка доступа предшествует приёму содержимого приложением. Файлы не публикуются как статические ресурсы. Скачивание выполняется авторизованным запросом; токен не передаётся в URL. Ответ использует безопасное имя вложения и запрет MIME-sniffing.
- UI различает выбор файла, загрузку, успешное сохранение и ошибку. Повторная отправка блокируется; после неопределённого результата сначала перечитываются метаданные. Уход со страницы отменяет клиентский запрос, но не трактуется как гарантированная отмена уже завершённого сохранения на сервере.
- Показывать индикатор выполнения запроса без выдуманных процентов. Обновлять данные после успеха, корректно обрабатывать истечение сессии и очищать временные браузерные ресурсы скачивания.
- Не показывать фиктивное состояние обработки: успешная загрузка означает «Файл сохранён», а не «Обработка запущена».
- Обновить документацию архитектуры, API, настроек размера, постоянного volume, резервного копирования БД вместе с файлами и восстановления.

## Testing Decisions

- Согласованная основная граница — сквозной браузерный сценарий с реальным API и тестовым хранилищем: войти, создать встречу, открыть её, загрузить небольшой допустимый файл, перезагрузить страницу, увидеть метаданные, скачать и сравнить байты оригинала.
- Проверять внешнее поведение, а не структуру компонентов, названия внутренних функций или число SQL-запросов.
- Существующие API-тесты авторизации и изоляции встреч расширить сценариями доступа к файлу, валидации размера и формата, пустого файла, отсутствующей встречи, повторной и конкурентной загрузки. Успех возвращает полный файл; отказ не оставляет видимой неполной записи.
- Проверить ошибки хранилища и транзакции: пользователь получает ошибку, файл не объявляется сохранённым, временные объекты удаляются. Проверить доступность сохранённого оригинала после перезапуска API с тем же хранилищем.
- Существующий frontend-тест на Node test runner и Playwright уже проверяет состояния запросов, повторную отправку и отмену при навигации с контролируемыми ответами API. Расширить его для ошибок загрузки, истечения сессии, неопределённого результата, клавиатуры и мобильного экрана. Такие проверки дополняют, но не заменяют реальный сквозной сценарий.
- Использовать отдельную мигрированную PostgreSQL-базу и временный каталог файлов. Проверить миграцию для существующих встреч без записи, сгенерированные типы, typecheck, lint и отсутствие ошибок браузера.

## Out of Scope

- Транскрибация, извлечение аудио, AI-анализ, итоговые заметки и запуск фоновой обработки.
- Проигрыватель, предпросмотр и перекодирование записи.
- Несколько файлов на встречу, замена и удаление записи, версии файлов.
- Прямая запись встречи в браузере, интеграции с сервисами видеозвонков.
- Drag-and-drop, возобновляемые и составные загрузки, процентный прогресс.
- Общий доступ по ссылке, доступ участников и изменение существующей модели владельца.
- S3, распределённое файловое хранилище, очереди и отдельные worker-сервисы.

## Further Notes

Смысл «файла встречи» как аудио- или видеозаписи, правило нескольких файлов(максимум 3), список форматов и 500 MiB — предложения этого черновика, а не ранее согласованные требования. Запрос пользователя явно включает загрузку, хранение, подготовку к последующей обработке и интерфейс отображения внутри встречи.

Пользователь согласовал локальный Markdown-трекер и основную границу проверки. Спецификация опубликована со статусом `ready-for-agent`; это готовность к реализации, а не отметка о выполнении или прохождении тестов. Каноническая версия находится в локальном трекере.
